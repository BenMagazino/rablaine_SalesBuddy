## Design Context

### Users
Azure technical sellers (cloud solution architects, technical specialists) who take notes during customer calls and need to retrieve them later. They work fast, context-switch constantly between customers, and use the app alongside Teams/Outlook. The app runs locally on their laptop - it's a personal productivity tool, not a team dashboard.

### Brand Personality
Professional, clean, functional. A tool that respects the user's time and doesn't get in the way. Think "well-organized notebook" not "enterprise dashboard."

### Aesthetic Direction
- **Visual tone:** Polished desktop workbench. Use the approved Graphite / Muted
  connected-pane design in `design-studies/`, not a new aesthetic direction.
  The completed redesign removes Bootstrap; legacy pages retain it only during migration.
- **Theme:** Light and dark mode (user toggle exists). Both must work well.
- **Typography:** The approved Segoe UI Variable Text / Segoe UI stack. No font download.
- **Color palette:** Graphite / Muted default dark; Graphite, Midnight, Harbor and
  Carbon dark/light pairs. Production tokens live in `static/css/ui-tokens.css`.
  Preserve seller/territory/topic identity and work-status meaning when replacing badges.
- **Anti-references:** Over-designed SaaS landing pages with gradients and glassmorphism. Generic AI-generated dashboards with hero metrics cards, card grids, gradient text. This is a work tool, not a marketing site.

### Design Principles
1. **Data density over decoration** - Users have lots of customers, notes, and engagements. Show more data, less chrome.
2. **Consistency over novelty** - Every page should feel like the same app. Badge colors, spacing, and patterns should be uniform.
3. **Speed over spectacle** - No animations that slow perception. No loading spinners where instant rendering is possible.
4. **Readability in both themes** - Every element must be readable in light and dark mode. Test both.
5. **Feature parity before sign-off** - Follow `docs/REDESIGN-WORKFLOW.md` and
   `docs/REDESIGN-PAGE-TRACKER.md`. Original controls and information must remain
   available unless the user explicitly approves a change. New components use
   app-owned styles and behavior, not Bootstrap utilities.
   Start with the tracker's compact handoff and the relevant page card. Historical
   checkpoint logs are archives, not active context. Follow the workflow's
   risk-based verification and stop rules instead of re-proving shared components.
6. **Desktop only** - Validate the desktop Electron viewport; do not add mobile
   layouts or resize user-shared browser pages for testing.
7. **Breadcrumb placement** - Use the full-width context bar immediately below
   the navbar, matching Home. All full pages use the shared `sb-context-bar`
   styles and centralized ancestry, not breadcrumbs inside page content.
   Non-home trails begin with a linked Home, use quiet `>` separators and finish
   with an unlinked current page. Home shows only its unlinked location label.
   Use real, canonical parents, never referrer history or fictional categories.
   Customer Revenue uses Home > assigned Seller > Customer > Revenue, omitting
   missing ownership. Revenue Analyzer belongs to Reports.
8. **Continuous workbench shell** - The shell owns the desktop window. Migrated
   standalone pages opt into `sb-page-frame` and divide an edge-to-edge surface
   into connected command/context bands and independently scrolling work regions.
   Borders separate functional regions, not a centered content card in outer
   gutters. Editor/detail widths may be constrained inside the surface.
   A compact status rail reports useful view scope or freshness; app/legal copy
   belongs in Help/About, not a website footer. Page compositions may vary.
   Roll out explicitly as each page migrates. Do not restyle legacy pages,
   embedded views or Home's already-connected grid implicitly.
9. **Contextual composition** - Full pages support sustained work; modals support
   focused inspection or editing without losing the parent context. Share domain
   content, actions, semantic colors and native styling, not necessarily layout.
   Compact modal lists may differ from queue/detail full pages. Do not embed the
   complete page shell or a miniature multi-pane application inside every modal.
10. **Task-shaped working regions** - Choose the composition around the work,
    not the old Bootstrap containers. Keep useful context beside the active
    reading/editing area when that improves understanding. Constrain tables to
    readable widths instead of stretching them to fill the window. Scope controls
    determine what is available; navigation chooses what is being examined within
    that scope and must not silently change saved filters. Suppress redundant
    choosers when there is only one destination. Keep broader aggregate views
    separate and explicitly label their scope. Use independent scrolling where
    it preserves context, without imposing a sidebar or identical split on every page.
11. **Sortable workbench tables** - Every column in every workbench table supports
    ascending/descending native header controls, including embedded and loaded
    shared fragments. Reuse `SBTableSort` with raw numeric/date keys rather than
    rounded currency or fiscal-label sorting. Keep summary rows pinned, unavailable
    values last, row identity/selection and filters intact, and restore independent
    pane sorting on Back. Sorting history must not reorder graphs or recalculate
    month-over-month changes.
